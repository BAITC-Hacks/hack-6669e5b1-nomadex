# P0: backend, общая БД и серверные права

Статус 23 сентября 2026: реализовано в ветке `codex/p0-backend-database-permissions` от main `e99b331`. Публичное развёртывание и проверка на двух физических устройствах ещё не выполнены; локальная проверка использует независимые браузерные сессии и HTTP-клиенты с одной БД.

## Запуск и окружения

Требуется Node.js >=24: используется встроенный [node:sqlite](https://nodejs.org/api/sqlite.html). Установите зависимости `npm ci`, скопируйте `.env.example` в `.env`, выполните `npm run dev`. Интерфейс — `http://127.0.0.1:5173`, API — `127.0.0.1:8787`; Vite проксирует `/api`. Без AI-ключа основной цикл работает с локальными подсказками.

| Переменная | Значение и ограничения |
|---|---|
| NODE_ENV | development, test или production; не используйте production для локальной демонстрации по HTTP |
| DATABASE_PATH | По умолчанию data/<NODE_ENV>.sqlite; в production обязательный явный путь на постоянном диске |
| HOST / PORT | По умолчанию 127.0.0.1 / 8787 |
| APP_ORIGINS | Точные адреса интерфейса через запятую, без пути и завершающего /; в production обязательны HTTPS |
| SERVE_WEB | 1 — сервер раздаёт готовую папку dist; 0 — API отдельно от Vite |
| OPENAI_API_KEY / OPENAI_MODEL | Только сервер; не добавлять в VITE_* или Git |
| SEED_PASSWORD | Только для явного заполнения пустой development-БД; не сохранять в репозитории |

Разные окружения должны иметь разные DATABASE_PATH, домены/cookie, ключи и backup-каталоги. Явный DATABASE_PATH из .env имеет приоритет над автоматическим именем: при смене NODE_ENV измените его тоже. Тесты создают отдельные временные БД в node_modules/.tmp и используют подмену AI, не production-данные.

Миграции применяются при запуске API или отдельно `npm run db:migrate`. В SQLite хранится `PRAGMA user_version`; неизвестная более новая версия останавливает запуск. Миграции выполняются под блокировкой и транзакцией. Перед обновлением сервера сделайте резервную копию. Выпущенные миграции не изменяют задним числом: добавляют следующую.

### Один сервер с готовым интерфейсом

```sh
npm run build
```

Для локальной проверки задайте в .env:
```dotenv
NODE_ENV=development
DATABASE_PATH=data/development.sqlite
SERVE_WEB=1
HOST=127.0.0.1
PORT=8787
APP_ORIGINS=http://127.0.0.1:8787
```

Запустите `npm run server` и откройте `http://127.0.0.1:8787`. Для проверки с двух аккаунтов используйте отдельные профили браузера. Для другого адреса добавьте его точный Origin.

### Пилот через HTTPS

Соберите интерфейс, настройте HTTPS reverse proxy перед Node, проксируйте весь сайт на loopback-порт 8787. Пример переменных (домен заменить своим):

```dotenv
NODE_ENV=production
DATABASE_PATH=/srv/nomadex/data/production.sqlite
SERVE_WEB=1
HOST=127.0.0.1
PORT=8787
APP_ORIGINS=https://nomadex.example
```

Два устройства должны обращаться к этому одному HTTPS-адресу. Не открывайте внутренний порт Node наружу, не используйте Vite dev/preview как публичный сервер. Production-cookie имеет Secure, поэтому вход по обычному HTTP в этом режиме работать не должен. Proxy должен ограничивать размер запроса, соединения и частоту запросов до приложения. Приложение намеренно не доверяет X-Forwarded-For: за proxy лимит по IP общий, нужны отдельные правила на внешнем входе. Защитите ОС, каталог БД, журнал и резервные копии правами сервисного пользователя; шифрование диска, TLS, управление секретами и расписание backup относятся к развёртыванию.

Не запускайте несколько копий с независимыми SQLite-файлами: это будут разные каталоги. SQLite-файл должен лежать на локальном постоянном диске одного хоста, не на общем сетевом диске. Для нескольких хостов потребуется PostgreSQL и перенос слоя хранения. Сейчас чтение/запись полного состояния и аудит-снимки рассчитаны на небольшой пилот.

## Аккаунты и видимость

Регистрация создаёт новый профиль бизнеса или команды. Один аккаунт соответствует одному профилю; произвольный вход под seed-ID удалён. Пароль 12–128 символов, scrypt с отдельной случайной солью; email нормализуется. Сессия на семь дней: случайный 256-битный токен, в БД только SHA-256 токена, HttpOnly/SameSite=Strict cookie, отзыв при выходе. CSRF-токен хранится в памяти клиента и проверяется вместе с allowlist Origin на записи.

- Бизнес создаёт, редактирует, подтверждает и публикует только свои задачи.
- Черновики скрыты от других бизнесов и команд.
- Все вошедшие видят опубликованные задачи и публичные профили.
- Команда отправляет один свой отклик. Его содержимое видят только она и владелец задачи.
- Владелец окончательно выбирает свои отклики. Выбранная команда отправляет свой результат; подтверждает только владелец.
- +10 вычисляется по уникальным подтверждённым результатам; клиент не может задать баллы или время.
- Суммарные баллы команд общедоступны внутри сервиса, тексты чужих результатов — нет.
- Регистрация/вход, команды и AI ограничены по частоте; AI доступен только вошедшему бизнесу.
- API не возвращает пароли, session hashes, таблицу аккаунтов или полные аудит-снимки.

Публикация фиксирует все поля карточки, включая рабочий контакт бизнеса. Используйте контакт, предназначенный для участников каталога. Нет email-verification, сброса пароля, MFA, администраторского интерфейса или участников внутри одной организации. Это отдельные задачи перед открытым публичным доступом.

## Данные и API

Реляционные таблицы: businesses, teams, accounts, tasks, proposals, decisions, results, sessions, receipts, audit, rate_limits и meta. Владельцы и связи защищены внешними ключами, повторные отклики — UNIQUE(task_id,team_id). Гибкие поля карточек хранятся в JSON-колонках с проверкой валидности, доменные связи дополнительно проверяются общей Zod-схемой. Таблица decisions фиксирует финальное решение, results — единственный результат на отклик.

| Метод и путь | Назначение |
|---|---|
| GET /api/health | Доступность процесса |
| POST /api/auth/register | email, password, name, role; для команды interests/skills/technologies |
| POST /api/auth/login | email, password |
| GET /api/auth/session | Текущий аккаунт и CSRF-токен |
| POST /api/auth/logout | Отзыв текущей сессии |
| GET /api/state | Видимая пользователю проекция, revision и teamPoints |
| POST /api/commands | Команда, expectedRevision и requestId (UUID) |
| GET /api/audit | Последние 100 собственных действий: только метаданные |
| POST /api/analyze-task | Прежний AI-контракт v2, теперь за авторизацией бизнеса |

Все POST принимают application/json и разрешённый Origin. Все авторизованные POST требуют X-CSRF-Token и session cookie. Полный контракт команд — shared/api.ts, правила переходов — shared/domain.ts. Пример конверта:

```json
{
  "requestId": "1361df48-5aeb-4b50-b785-a4ba6d6143f9",
  "expectedRevision": 3,
  "command": { "type": "create" }
}
```

Успех возвращает актуальную проекцию и createdId при создании. Повтор той же команды с тем же requestId не выполняет её снова, даже если исходный ответ потерян. Тот же ID с другим содержимым — 409. История квитанций сохраняется в БД, а не в памяти процесса.

401 — нет сессии; 403 — роль/CSRF/Origin; 404 — неизвестный или скрытый объект; 409 — конфликт версии/повтор ID; 422 — недопустимый переход; 429 — лимит. Клиент обновляет каталог раз в пять секунд. При сетевой ошибке не показывает фиктивный успех.

### Конкурентность и черновики

Все изменения выполняются атомарно с проверкой общей revision, аудитом и квитанцией в BEGIN IMMEDIATE. Эта первая реализация консервативна: даже изменение другой задачи или регистрация аккаунта может вызвать конфликт сохранения. Автоматического слияния текста нет; будущая оптимизация — версии отдельных объектов.

Редактор хранит несохранённый текст в памяти формы, явно сохраняет его и запрещает подтверждение до сохранения. Фоновое обновление не затирает грязную форму. При конфликте скопируйте нужный текст, нажмите «Загрузить серверную версию», внесите правки и сохраните. При уходе из черновика есть предупреждение. Несохранённый текст не переживает закрытие браузера/сбой процесса. Старое localStorage не импортируется автоматически: нельзя назначить его данные реальным владельцам без отдельного проверяемого переноса.

## Seed и обслуживание

`npm run db:seed` импортирует docs/source-data.json через прежнюю проверенную миграцию домена в **пустую** базу и создаёт шесть аккаунтов с исходными ID. Пароль берётся из SEED_PASSWORD, соли разные. Email бизнеса — business-demo@demo.invalid; адреса остальных команда печатает после успеха. Никакого встроенного пароля нет. Для новой демонстрации выберите новый DATABASE_PATH вместо удаления текущих данных.

### Backup и restore

Создайте каталог backups заранее. Каждой копии давайте новое имя:

```sh
npm run db:backup -- backups/nomadex-2026-09-23.sqlite
npm run db:restore -- backups/nomadex-2026-09-23.sqlite data/restored-2026-09-23.sqlite
```

Backup использует SQLite backup API, учитывает WAL и проверяет quick_check/foreign_key_check. Исходная БД может оставаться открытой. Существующий файл назначения никогда не перезаписывается. После сбоя копирования может остаться незавершённый файл: используйте новое имя и проверьте результат, не считайте наличие файла успешным backup.

Restore создаёт **новый** файл. Проверьте его в отдельном тестовом запуске; затем остановите рабочий сервер, измените DATABASE_PATH и запустите его снова. Исходную БД и резервную копию сохраните до подтверждения результата. Копии содержат аккаунты, хеши паролей, действующие сессии и аудит: хранить как чувствительные данные, вне dist и публичных каталогов. Простое копирование одного живого .sqlite без WAL не заменяет эту команду.

### Восстановление по журналу

Аудит фиксирует снимки доменных данных до/после register, seed, create, edit, confirm, publish, submitProposal, finalizeDecision, submitResult, confirmResult и recover. Пароли и токены в снимки не входят. Неизменяющее повторное подтверждение не создаёт ещё одно начисление/событие.

Найдите нужный event-id по метаданным собственного /api/audit или read-only просмотром таблицы audit оператором. Создайте backup и выполните:

```sh
npm run db:recover -- backups/nomadex-2026-09-23.sqlite 42 data/recovered-event-42.sqlite
```

42 — пример, замените существующим ID. Команда восстанавливает **весь рабочий процесс после этого события**, а не только одну задачу: задачи, предложения, решения и результаты. Текущие аккаунты и профили сохраняются, сессии и квитанции очищаются, новая запись recover добавляется в журнал. Более поздние рабочие изменения откатываются только в новой копии; исходник не меняется. Это инструмент оператора, а не публичный endpoint. Проверьте полученную копию и только затем переключайте рабочий сервер. При ошибке не переключайте DATABASE_PATH.

Полные снимки упрощают восстановление пилота, но увеличивают журнал и содержат приватные черновики. Перед масштабированием нужны политика хранения/удаления персональных данных, архивирование, независимая защищённая копия аудита и автоматизированная проверка backup по расписанию. Журнал не защищён от администратора, имеющего запись в сам файл БД.

## Проверка и следующий шаг

Пройдены typecheck, 68 автоматических тестов и production-сборка. 12 новых тестов покрывают реальные HTTP-запросы, файл SQLite, два аккаунта, права/CSRF, публикацию–отклик–решение–результат, +10 без повторов, параллельные изменения, повтор запроса, перезапуск, backup/restore, восстановление по событию, seed, AI-gateway, ограничения входа, выдачу файлов и отдельные подключения к БД.

В двух независимых браузерных сессиях проверены регистрация бизнеса/команды, сохранение, общий каталог, отклик, выбор, результат, подтверждение и +10 после перезагрузки. Это локальная проверка, не свидетельство развёртывания на двух физических устройствах. Реальный OpenAI ранее принят в MVP; здесь проверялся защищённый gateway с подменённым провайдером, новых платных вызовов не выполнялось.
