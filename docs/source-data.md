# Исходные данные MVP

Синтетический набор версии 2: один бизнес, 5 черновиков разной полноты, 5 опубликованных карточек, 5 команд и 5 откликов. Все сведения вымышлены для демонстрации, не содержат персональных и чувствительных признаков и не являются результатом AI. Упомянутые таблицы, расписания и отзывы описывают условия вымышленных заказчиков; реальные файлы этих материалов не входят в набор и для показа платформы не нужны.

## Форматы и загрузка

- [source-data.json](source-data.json) — основной источник данных.
- [source-data.csv](source-data.csv) — полное представление тех же записей: одна строка на сущность, все поля отдельными колонками, без сокращения текстов.
- Этот документ содержит полные записи из JSON и поясняет загрузку и сценарий показа.

`schemaVersion: 2` обозначает исправленную структуру набора; `scoringVersion: 1` — неизменные веса рейтинга. Старую структуру версии 1 не загружать как новую без явного сброса демоданных.

### CSV-контракт

UTF-8, разделитель — запятая, стандартное экранирование двойными кавычками. `entity_type` принимает business / draft / task / team / proposal; коллекции JSON соответственно businesses / drafts / tasks / teams / proposals. Во всех строках `schemaVersion` равен 2. Остальные имена колонок совпадают с ключами JSON.

Пустая ячейка означает, что поле неприменимо к этому типу записи и его не нужно добавлять. Литерал `null` означает известное поле без значения. Числа `schemaVersion`, `scoringVersion`, `readinessScore` преобразуются в целые; `confirmed` — true/false. `skills`, `technologies`, `plan`, `questions`, `answers` содержат JSON-массивы и разбираются через JSON.parse, а не делением строки по запятой. Остальное — строки; publishedAt — ISO 8601 UTC или null. CSV следует разбирать полноценным CSV-парсером, не split(',').

При восстановлении JSON вынести schemaVersion в корень, распределить строки по пяти коллекциям, удалить entity_type и schemaVersion из сущностей и применить указанные преобразования типов. Результат должен в точности совпасть с JSON, включая null, массивы и полные тексты.

### Инициализация приложения

1. Загружать seed только при отсутствии сохранённого состояния; не затирать данные пользователя при перезагрузке.
2. Объединить drafts и tasks в коллекцию задач приложения, сохранив id и status. Сохранить businesses, teams и proposals; results инициализировать пустым массивом.
3. Черновики имеют businessId, confirmed=false, publishedAt=null; они доступны бизнесу, но отсутствуют в каталоге. При публикации черновик сохраняет свой id и меняет статус, не перезаписывая похожую готовую карточку.
4. Готовые карточки уже подтверждены вымышленным бизнесом: confirmed=true, publishedAt задан. Повторное подтверждение и редактирование опубликованной карточки не нужны. Решений ещё нет: decisionFinalizedAt=null, все отклики submitted.
5. Пересчитать рейтинг по правилам ниже и сравнить с readinessScore. Несовпадение — ошибка данных, а не повод показывать произвольный балл. Баланс всех команд первоначально 0; он вычисляется по подтверждённым результатам.
6. Ссылки откликов ведут на существующие разделы этого документа — это демонстрационные материалы предложений, не портфолио и не готовые результаты работы. При использовании в UI показывать «Демо-предложение» и либо открывать соответствующий раздел документа, либо отображать его локально по id отклика. Для реального ввода ссылка может быть внешним HTTP(S)-адресом; не принимать javascript: и другие исполняемые схемы.

## Правила рейтинга

Все шесть ключей присутствуют даже у неполных записей. Неизвестные и неполные критерии обозначены null, а не фразами «уточняется». Заполненный текст содержит необходимые части критерия; его вес начисляется целиком. Неполный ввод в UI можно сохранять в ответах, но до уточнения не считать готовым критерием. AI не выставляет баллы. Это оценка заполненности, не автоматическая проверка правдивости.

| Поле | Баллы |
|---|---:|
| problemContext | 20 |
| expectedResult | 20 |
| acceptanceCriteria | 20 |
| scope | 15 |
| resources | 15 |
| timingConstraints | 10 |

Расчёт: сумма весов полей со значением, отличным от null и пустой строки. В данном наборе все ненулевые поля содержательно заполнены. При вводе «не знаю», «уточняется» или выборе «пока неизвестно» приложение сохраняет соответствующий критерий как null, а исходный ответ отдельно. Отсутствие дедлайна или ресурсов можно явно подтвердить текстом — это известное условие и даёт баллы.

| Карточка | Рейтинг | Незаданные критерии |
|---|---:|---|
| task-001 | 100 | Нет |
| task-002 | 90 | timingConstraints |
| task-003 | 75 | resources, timingConstraints |
| task-004 | 55 | acceptanceCriteria, resources, timingConstraints |
| task-005 | 40 | acceptanceCriteria, scope, resources, timingConstraints |

Сортировка: readinessScore по убыванию, publishedAt по убыванию, id по возрастанию. Начальный порядок task-001 → task-002 → task-003 → task-004 → task-005.

## Сквозной демонстрационный прогон

1. После первичной загрузки убедиться, что видны 5 опубликованных карточек, 5 команд и 5 откликов; 5 черновиков видны только бизнесу. Существующие отклики просматривать, а не отправлять заново.
2. Открыть task-draft-001 и получить минимум три вопроса через обязательную интеграцию OpenAI. Представитель бизнеса сам отвечает на них. Можно ввести такие новые синтетические ответы: результат — реестр заявок со статусом и ответственным; приёмка — 20 заявок без дубликатов и фильтрация по статусу; границы — ручное добавление без внешних интеграций; ресурсы — синтетические заявки; срок — дедлайна нет, только локальные обезличенные данные. Это ввод человека во время показа, не факты, извлечённые AI из короткого описания.
3. Отредактировать карточку, проверить рост рейтинга с 20 до 100 после заполнения всех критериев. Подтвердить и опубликовать текущий task-draft-001: он сохраняет id, получает publishedAt и попадает в каталог. Готовая task-001 остаётся отдельной записью. Публикация неполной подтверждённой карточки также допустима.
4. Переключить team-003, team-004 и team-005 и создать по новому отклику на task-draft-001 с новыми id. Ввести идею, план, результат, срок, навыки и ссылку. На этой задаче ещё нет откликов, поэтому конфликтов с seed не будет. Повтор той же пары taskId/teamId должен быть запрещён.
5. На task-draft-001 выбрать две команды из трёх и подтвердить решение. На task-002 выбрать единственную team-003, на task-005 явно не выбрать никого. Эти независимые задачи позволяют показать все три варианта решения без сброса или пересмотра финального выбора. Готовые proposal-001 и proposal-002 на task-001 дополнительно подходят для просмотра сравнения двух предложений.
6. Выбранная команда отправляет текст результата своего единственного этапа, бизнес подтверждает. Начисляется ровно +10; повторное подтверждение и перезагрузка баллы не увеличивают. Невыбранная команда не может отправить результат через интерфейс.

Исходные данные не назначают исполнителей и не содержат подтверждённых результатов. Все решения и начисления выполняются во время показа человеком. Для нового прогона использовать явный сброс демоданных с подтверждением.
